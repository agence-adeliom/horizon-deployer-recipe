# Spec : authentification HTTP des préproductions par .htpasswd

Tâche ClickUp : https://app.clickup.com/t/42608153/1241hmhf3kr

Statut : validée en discussion le 26/11/2026, pas encore implémentée.

## Besoin

Les préproductions sont aujourd'hui protégées par un `mu-plugin` ou un provider Acorn. Cette protection ne couvre que les requêtes servies par PHP : les médias, les assets et tout fichier statique restent accessibles à qui connaît l'URL.

Le recipe installe donc une authentification HTTP au niveau d'Apache (`.htaccess` + `.htpasswd`), avec des identifiants propres à chaque préproduction. Les identifiants sont rangés à la main dans Bitwarden par la personne qui lance la tâche.

## Décisions

| Sujet | Décision |
|---|---|
| Activation | Réglage `http_auth: true` par hôte dans `.inventory.yaml`, désactivé par défaut |
| Garde-fou | Refus sur un hôte que WordPress considère en production |
| Tâches | `http-auth:setup`, `http-auth:update` et `http-auth:remove`, lancées à la main, plus une tâche cachée accrochée au déploiement |
| Mise à jour | `http-auth:update` change l'identifiant et le mot de passe, en ne réécrivant que le `.htpasswd` |
| Identifiant | `http_auth_user`, `adeliom` par défaut |
| Mot de passe | Saisi deux fois en masqué ; une saisie vide le fait générer, avec affichage unique |
| Hash | Bcrypt (`$2y$`) calculé en PHP sur le poste local |
| Fichiers | `.htpasswd` dans `{{deploy_path}}/shared/`, hors de la racine publique ; bloc balisé dans le `.htaccess` |
| Exceptions | IP du serveur, `/.well-known/acme-challenge/`, chemins configurables |
| Nginx | Refus avec message, sans aucune écriture |
| Protection existante | `curl` sans identifiants depuis le poste local : une 401 déclenche un avertissement et une confirmation |
| Retrait | `http-auth:remove` retire le bloc ; le `.htpasswd` reste pour une réactivation |
| Écritures | Toute question qui écrit a "non" pour défaut ; rien n'est écrit en `-n` |

## Configuration

| Clé | Défaut | Rôle |
|---|---|---|
| `http_auth` | `false` | Active la protection de l'hôte. À poser dans l'inventaire, hôte par hôte |
| `http_auth_user` | `adeliom` | Identifiant écrit dans le `.htpasswd` par `setup`, et réponse proposée par `update` |
| `http_auth_realm` | `Accès restreint` | Texte affiché par le navigateur (`AuthName`) |
| `http_auth_htaccess` | `web/.htaccess` | Chemin du `.htaccess`, relatif à la release |
| `http_auth_htpasswd` | `{{deploy_path}}/shared/.htpasswd` | Chemin du `.htpasswd` sur le serveur |
| `http_auth_except_paths` | `['/.well-known/acme-challenge/']` | Préfixes d'URL servis sans authentification (webhooks, par exemple) |
| `http_auth_allow_ips` | `[]` | IP autorisées sans authentification, en plus de celle détectée pour le serveur |

Exemple d'inventaire :

```yaml
hosts:
  staging:
    http_auth: true
  recette:
    http_auth: true
    http_auth_user: client
    http_auth_except_paths: ['/.well-known/acme-challenge/', '/wp-json/gf/v2/webhooks/']
```

Le mot de passe n'apparaît jamais dans l'inventaire ni dans le dépôt.

## Garde-fou production

Le type d'environnement se lit comme dans `roles:check`, à partir de `WP_ENVIRONMENT_TYPE` et `WP_ENV` dans `{{deploy_path}}/shared/.env` (`rolesCheckHostEnvironmentValues()` puis `rolesCheckEnvironmentType()`).

- Type `production` : refus, quel que soit `http_auth`. `WP_ENV=preprod` donne `production` pour WordPress et bloque donc aussi ; le message l'explique et invite à passer `WP_ENV=staging`.
- Type `staging`, `development` ou `local` : la tâche continue.
- Type introuvable (aucune des deux variables) : refus si `transferIsProtected()` est vrai, sinon poursuite avec une ligne d'information.

Ces deux fonctions portent le préfixe `rolesCheck` alors qu'elles deviennent communes. Elles sont à renommer (`transferHostEnvironmentValues()`, `transferEnvironmentType()`) dans le même lot, avec leurs tests. `transferHostEnvironmentValues()` lit aussi `WP_HOME`, utile au `curl` et à la sonde.

## Tâche `http-auth:setup <hôte>`

Commence par `transferResetState()` si elle crée un répertoire de travail, et suit alors le triptyque de nettoyage (`invoke('transfer:cleanup')`, `fail()` en fin de fichier). Sinon elle n'y est pas soumise, comme `wp:update-db`.

Étapes, dans l'ordre :

1. **Réglage.** `http_auth` faux : message expliquant la clé à poser dans l'inventaire, sortie sans erreur.
2. **Garde-fou production**, décrit plus haut.
3. **URL du site.** `WP_HOME` lu dans `shared/.env`. Absente : erreur, rien n'est écrit.
4. **Protection existante.** `curl -sS -o /dev/null -w '%{http_code}'` sans identifiants sur `WP_HOME`, lancé depuis le poste local (depuis le serveur, la requête passerait par l'exception d'IP une fois la protection posée). Une 401 signale une protection déjà en place : avertissement et `transferConfirm('Installer quand même ?', false)`. Une requête en échec (DNS, TLS) n'est qu'un avertissement.
5. **Mode non interactif.** En `-n`, la tâche affiche ce qu'elle ferait et s'arrête.
6. **Confirmation.** `transferConfirm('Installer l'authentification HTTP sur <hôte> ?', false)`.
7. **Sonde Apache**, décrite plus bas. Échec : refus avec message, rien n'est écrit hors de la sonde.
8. **Mot de passe**, décrit plus bas.
9. **Écriture du `.htpasswd`**, si on en a créé ou régénéré un.
10. **Écriture du bloc** dans le `.htaccess` de la release courante (`{{current_path}}`), résolu par `readlink -f` pour écrire dans `shared/` s'il y est partagé.
11. **Vérification.** Nouveau `curl` sans identifiants : 401 attendu. Avec les identifiants : 200 ou 30x attendu (impossible si le `.htpasswd` existant a été conservé, faute de connaître le mot de passe : étape sautée). Échec : le bloc est retiré et la tâche échoue.
12. **Récapitulatif.** URL, identifiant et, s'il a été généré, mot de passe en clair, avec la consigne de le ranger dans Bitwarden : il ne sera plus affiché.

### Sonde Apache

Savoir si le serveur honore un `.htaccess` d'authentification ne se lit pas de façon fiable dans une en-tête `Server` (souvent masquée sur les mutualisés). La tâche le vérifie par l'effet :

1. Elle crée dans la racine publique un dossier au nom aléatoire (`horizon-http-auth-<aléa>/`, sans point initial : certains hébergeurs refusent les chemins en `.`, ce qui fausserait la sonde) contenant un `.htaccess` qui exige une authentification et un `index.php` qui affiche `$_SERVER['REMOTE_ADDR']`.
2. Elle interroge ce dossier en `curl` depuis le poste local :
   - 401 : Apache applique les directives, la sonde est concluante ;
   - 200 : le `.htaccess` est ignoré (Nginx, ou `AllowOverride` sans `AuthConfig`), refus ;
   - 500 : directives refusées (Apache 2.2, module manquant), refus.
3. Elle retire l'exigence d'authentification du `.htaccess` de la sonde, puis interroge l'`index.php` depuis le serveur. L'adresse affichée est celle qu'Apache voit pour les requêtes du serveur vers lui-même (WP-Cron, santé du site) : c'est l'IP détectée pour l'exception.
4. Elle supprime le dossier, y compris en cas d'échec (`try/finally`).

Derrière un proxy (Cloudflare, frontal d'hébergeur), l'adresse vue peut être celle du proxy. Le récapitulatif l'affiche donc, et `http_auth_allow_ips` permet de corriger.

### Mot de passe

- **`.htpasswd` déjà présent** : `setup` le conserve sans poser de question, signale l'identifiant qu'il contient et renvoie vers `http-auth:update` pour changer les identifiants. Un identifiant différent de `http_auth_user` déclenche un avertissement.
- **Saisie** : `askHiddenResponse()`, deux fois. Les deux valeurs diffèrent : nouvelle saisie, trois essais au plus.
- **Saisie vide** : génération locale par `random_bytes()`, 24 caractères alphanumériques (sans caractères ambigus ni caractères spéciaux, pour une saisie facile sur mobile).
- **Hash** : `password_hash($motDePasse, PASSWORD_BCRYPT)`, en local. Seul le hash part vers le serveur, ce qui garde le mot de passe hors des commandes visibles en `-vvv`.
- **Écriture** : `printf '%s\n' <ligne>` vers un fichier temporaire de `shared/`, puis `mv`, droits `644` (l'utilisateur d'Apache diffère parfois de celui du compte SSH, et le fichier est hors de la racine publique).

## Bloc écrit dans le `.htaccess`

Placé en tête du fichier, avant les règles de réécriture de WordPress. Le texte entre les balises est entièrement regénéré à chaque écriture : un bloc identique n'est pas réécrit, un bloc différent est remplacé.

```apache
# BEGIN Horizon HTTP auth
# Géré par horizon-deployer-recipe (http-auth:setup). Ne pas modifier à la main.
AuthType Basic
AuthName "Accès restreint"
AuthUserFile /srv/staging/shared/.htpasswd
<RequireAny>
    Require ip 127.0.0.1 ::1 203.0.113.10
    Require expr %{REQUEST_URI} =~ m#^/\.well-known/acme-challenge/#
    Require valid-user
</RequireAny>
# END Horizon HTTP auth
```

- `AuthUserFile` reçoit un chemin absolu, résolu sur le serveur (`deploy_path` en `~/` compris).
- Chaque préfixe de `http_auth_except_paths` devient une ligne `Require expr`, échappé pour l'expression régulière.
- Fichier `.htaccess` absent : créé avec le seul bloc.

## Tâche cachée `deploy:http-auth`

Si le `.htaccess` est versionné, chaque déploiement le remplace par la version du dépôt, sans le bloc. La tâche cachée réinjecte le bloc dans `{{release_path}}` :

- accrochée par `before('deploy:symlink', 'deploy:http-auth')`, après test d'existence de `deploy:symlink`, comme les autres points d'accroche ;
- inerte, sans commande distante, si `http_auth` est faux ;
- inerte, avec un avertissement, si `.htpasswd` est absent (installation jamais faite) ;
- garde-fou production appliqué : en production, rien n'est écrit et un avertissement est affiché ;
- aucune question ; elle ne réécrit pas le `.htpasswd` et n'appelle pas la sonde ;
- l'IP du serveur, connue seulement après la sonde, est relue dans le bloc présent dans `{{current_path}}` avant la bascule ; à défaut, le bloc ne contient que `127.0.0.1 ::1` et `http_auth_allow_ips`.

Un échec de la réinjection fait échouer le déploiement, avant la bascule. Mettre en ligne une préproduction sans protection serait une régression silencieuse.

## Tâche `http-auth:update <hôte>`

Change l'identifiant et le mot de passe d'une protection déjà installée. Le bloc du `.htaccess` désigne le `.htpasswd` par son chemin, qui ne change pas : seul le `.htpasswd` est réécrit, sans sonde ni modification du `.htaccess`.

1. **Installation existante.** `.htpasswd` absent ou bloc absent du `.htaccess` de `{{current_path}}` : message renvoyant vers `http-auth:setup`, sortie sans écriture.
2. **Garde-fou production**, comme pour `setup`.
3. **Mode non interactif.** En `-n`, la tâche affiche l'identifiant actuel et s'arrête.
4. **Identifiant.** Question `ask()`, avec `http_auth_user` pour réponse proposée. Une réponse différente de `http_auth_user` déclenche un rappel de mettre à jour `.inventory.yaml`. Identifiant vide ou contenant `:` : nouvelle question.
5. **Mot de passe**, comme pour `setup` (saisie masquée confirmée, ou génération sur saisie vide).
6. **Confirmation.** `transferConfirm('Remplacer les identifiants HTTP de <hôte> ?', false)`.
7. **Écriture.** L'ancien `.htpasswd` est copié en `.htpasswd.bak` dans `shared/`, puis le nouveau est écrit dans un fichier temporaire et mis en place par `mv`.
8. **Vérification.** `curl` depuis le poste local avec les nouveaux identifiants : 200 ou 30x attendu. Échec : `.htpasswd.bak` est remis en place et la tâche échoue. Succès : `.htpasswd.bak` est supprimé.
9. **Récapitulatif.** URL, identifiant et mot de passe en clair, avec la consigne de mettre à jour l'entrée Bitwarden : il ne sera plus affiché.

## Tâche `http-auth:remove <hôte>`

1. `-n` : affiche ce qu'elle ferait et s'arrête.
2. `transferConfirm('Retirer l'authentification HTTP de <hôte> ?', false)`.
3. Retire le bloc balisé du `.htaccess` de `{{current_path}}` (le fichier reste en place, même vide).
4. Conserve le `.htpasswd`.
5. Si `http_auth` vaut encore `true`, avertit que le prochain déploiement remettra la protection, et invite à passer la clé à `false` dans l'inventaire.

Pas de garde-fou production : retirer une protection posée par erreur doit rester possible.

## Limites connues

- **Nginx** : non pris en charge, la sonde le détecte et la tâche refuse.
- **Mots de passe d'application WordPress** : ils passent eux aussi par l'en-tête `Authorization: Basic`, qui entre en conflit avec l'authentification HTTP. Une intégration qui en dépend doit passer par `http_auth_except_paths` ou `http_auth_allow_ips`.
- **Proxy en frontal** : l'IP détectée peut être celle du proxy, voir la sonde.
- **Protection existante en PHP** : la tâche ne la retire pas. Avec les deux, le navigateur demande deux fois des identifiants. L'ancien mécanisme est à retirer du projet, par un commit dans son dépôt.

## Tests

### Unitaires (`tests/unit/http-auth.test.php`)

- `http_auth` faux : aucune commande distante, pour `setup` comme pour `deploy:http-auth`.
- Garde-fou : `WP_ENV=production`, `WP_ENV=preprod`, `WP_ENVIRONMENT_TYPE=production` avec `WP_ENV=staging`, type introuvable avec et sans `transfer_protected`.
- `-n` : aucune écriture.
- Confirmation refusée, et fin d'entrée sans TTY (défaut "non") : aucune écriture.
- `curl` initial en 401 : avertissement et question ; refus : aucune écriture.
- Sonde en 200 et en 500 : refus, dossier de sonde supprimé.
- Mot de passe : saisie confirmée, saisies différentes puis concordantes, trois échecs, saisie vide (génération, 24 caractères, affichage unique), `.htpasswd` existant conservé par `setup` avec renvoi vers `update`.
- `http-auth:update` : refus sans installation existante, refus en production, `-n` sans écriture, identifiant proposé depuis l'inventaire, rappel d'inventaire sur un identifiant différent, identifiant vide ou avec `:` redemandé, confirmation refusée sans écriture, restauration de `.htpasswd.bak` si la vérification échoue, suppression de la copie si elle réussit, `.htaccess` jamais modifié.
- Hash : vérifiable par `password_verify()`, mot de passe en clair absent de toutes les commandes enregistrées.
- Bloc : génération (IP, exceptions échappées, chemin absolu), insertion dans un fichier sans bloc, remplacement d'un bloc différent, aucune écriture pour un bloc identique, création d'un fichier absent. Exécuté pour de vrai sur un dossier temporaire (`Shell::$reel`).
- Vérification finale en échec : bloc retiré, tâche en échec.
- `deploy:http-auth` : réinjection dans `{{release_path}}`, IP reprise du bloc de `{{current_path}}`, avertissement sans `.htpasswd`, rien en production.
- `http-auth:remove` : bloc retiré, `.htpasswd` conservé, avertissement si `http_auth` est vrai.
- Renommage des fonctions d'environnement : les cas existants de `roles.test.php` passent sous les nouveaux noms.

Chaque fonction nouvelle ou renommée a sa ligne dans `tests/COUVERTURE.md`.

### Intégration

Les serveurs de test n'ont pas de serveur web. Un scénario `90-http-auth.sh` demande d'ajouter Apache (avec `AllowOverride All`) à l'image d'un des deux serveurs, et un hôte servi par un serveur sans Apache pour le cas du refus. Ce coût est à arbitrer au moment de l'implémentation.
